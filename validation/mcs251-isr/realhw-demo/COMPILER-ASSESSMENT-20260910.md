# MCS251 编译器与工具链不足评估

**依据：G12K128 T10 单层实机 Demo 开发与用户实板反馈**  
**日期：2026-09-10**  
**性质：工程评估，不是完整编译器审计或 T10 资格结论**

## 1. 摘要

当前工具链已经能够生成在 G12K128 上运行的 C Timer0 ISR，并在本次特定负载下通过单次与 10000 次逐轮实板检查。没有从这份结果中发现已定案的 ISR 寄存器保存/恢复错误。

本次更明确暴露的是工程成熟度问题：

1. 普通 C 报告代码出现相对分支越界，需通过 noinline 调整函数规模绕过。
2. 静态参数槽 ABI 对中断可重入存在约束，夹具必须主动规避共享调用状态。
3. 低地址数据分配窗口紧张，失败诊断不足以直接定位对象、容量和冲突。
4. 当前采用的手写汇编与 ELF 链接路径衔接不顺，需要额外包装机器码。
5. 最终 ELF 缺少符号表，错误信息和机器码的源码关联能力不足。
6. PSW/PSW1、所有寄存器主动破坏覆盖及嵌套等仍是验证欠账，不能误报为已经确认的编译器缺陷。

**总体判断：受控的单层中断应用已具备实板依据；复杂中断应用所需的可重入保障、诊断能力及完整验证仍不充分。**

## 2. 证据基线

- 源码：[main.c](main.c)、[isr.c](isr.c)、[helper.c](helper.c)、[gen-sentinel.py](gen-sentinel.py)。

- 产物：[release/t10-g12.hex](release/t10-g12.hex)、[map](release/t10-g12.map)、[manifest](release/manifest.json)。
- 优化级别：O2，无 LTO；C 经 Clang→LLVM ELF，汇编哨兵经 sdas251/sdld→机器码→ELF 包装。
- HEX SHA256：`ce7100ad4487cc5fd3050e1684c5b2c70b1deea5b6c2d5e377f861c6d60cdd3a`。
- 硬件目标：STC32G12K128；固件要求 IRC=24MHz、UART1=115200/8N1。
- 此次 T10 Demo 按用户要求未运行模拟器，也未执行动态故障注入；静态检查不替代动态证据。
- 工具身份已记录，但未核定为 T09 冻结工具组合，不把开发验证产物等同于正式资格资产。

### 2.2 用户实板反馈

单次结果（保留关键原始行）：

```text
T10-G12-v1 RESULT case=s status=PASS completed=0001 attempted=0001 code=00 addr=0000 expected=00 actual=00 hits=01 SP=0600/0600 PSW_RAW=00/00 PSW1_RAW=00/20
FLAGS=NOT_TESTED NESTED=NOT_TESTED WINDOWS=NOT_TESTED
```

10000 次结果：

```text
T10-G12-v1 PROGRESS completed=25E4
T10-G12-v1 PROGRESS completed=2648
T10-G12-v1 PROGRESS completed=26AC
T10-G12-v1 PROGRESS completed=2710
T10-G12-v1 RESULT case=r status=PASS completed=2710 attempted=2710 code=00 addr=0000 expected=00 actual=00 hits=01 SP=0600/0600 PSW_RAW=00/00 PSW1_RAW=00/20
FLAGS=NOT_TESTED NESTED=NOT_TESTED WINDOWS=NOT_TESTED
```

`0x2710=10000`。长测执行 10000 轮独立中断并逐轮检查，不是仅打印同一次测试 10000 遍；测试结束后的重复报告则是同一最终结果重发。`hits=01` 是最后一轮的计数，不是累计中断数。

来源为用户反馈的串口日志，不是代理直接操作硬件所得。SHA256 标识交付文件，未做芯片 Flash 回读校验。release 中 manifest、STATIC-CHECKS 的 NOT_RUN 描述的是构建时状态；本节补充后续用户实板证据，不改写冻结构建记录。

### 2.3 已覆盖与未覆盖

实板 PASS 表明：该测试中每轮 ISR 执行一次，R0–R31、DPL/DPH/DPXL 返回值与哨兵一致，SP 恢复、guard 正确、helper 计算结果正确、共享 byte 修改保留。

静态机器码显示：ISR 软件保存37字节，局部数组8字节，跨文件 helper 通过 ECALL 调用，helper 局部4字节并以 ERET 返回，ISR 尾声逆序恢复后 RETI。

不包含：PSW/PSW1严格恢复断言、两级嵌套、每条序言/尾声指令处的抢占、所有寄存器均被主动修改后的恢复、默认入口和精确硬件时序。

## 3. 问题与改进项总表

下列编号只用于本评估，不替代既有 Rxx 或 Txx 编号。

| 编号 | 项目 | 分类 | 优先级 |
|---|---|---|---|
| E1 | 相对分支越界无法自动处理 | 本次实际编译失败，根因待定位 | 高 |
| E2 | 静态参数槽与中断可重入约束 | ABI 设计限制及诊断需求 | 高 |
| E3 | 数据分配窗口与链接错误信息 | 内存模型限制、工具易用性问题 | 中 |
| E4 | 手写汇编接入 ELF 需要额外桥接 | 本次使用路径的工具链衔接问题 | 中 |
| E5 | 最终 ELF 无符号、诊断位置不足 | 本次产物可调试性问题 | 中 |
| V1 | PSW1_RAW=00/20 未解释 | 实测差异，尚非已定案缺陷 | 高 |
| V2 | 寄存器破坏、嵌套和窗口覆盖不足 | 测试覆盖不足 | 高 |

## 4. E1：相对分支越界需要 C 层绕过

### 观察

初始报告程序在 LLVM 生成对象阶段出现多条：

```text
<unknown>:0: error: MCS251 PC-relative branch out of range
```

随后给 main.c 内部辅助函数增加 `__attribute__((noinline))`，编译通过。现有 [main.c](main.c) 保留这一绕过，涉及 putc、puts、hex8、hex16、pause、uart_init、error、same、run_one、report。

### 判断

当前后端至少没有正确处理本次代码形态需要的超范围分支。它把机器指令距离限制暴露给 C 用户，迫使用户改变内联策略。仅凭这次观察，尚不能确定是缺失分支松弛、某类分支漏处理，还是估算与最终布局不一致；不得直接宣称所有长分支均不支持。

### 影响与建议

报告格式、内联决策或优化级别变化可能让原本可编译的代码失败。建议优先保存失败 IR 和最小复现，再定位具体 opcode/分支目标；支持时自动扩展为等价长跳转，不支持时给出函数和分支位置。

验收建议：距离边界内/外、前向/后向分支、不同优化级别、函数布局变化均有回归；无需通过用户添加 noinline 才可编译。验证范围不能只看编译通过，还应核对控制流等价性。

证据限制：失败信息在本次开发会话中实际出现；发布目录保留的是绕过后的成功产物，尚未归档最小失败 IR。noinline 是当前绕过，不是后端修复。

## 5. E2：静态参数槽 ABI 对中断重入不友好

### 观察

[release/t10-g12.map](release/t10-g12.map) 包含：

```text
main.o:.mcs251.DSEG.7 0x0065 +0x4
main.o:.mcs251.DSEG.8 0x0069 +0x3
main.o:.mcs251.OSEG.9 0x006c +0x4
```

普通 C 调用使用静态参数槽。此次夹具专门避免前台被打断时调用 ISR 所用 helper；helper 采用单参数、独立翻译单元，并未引入除法等未经审计的隐式运行时调用。

### 判断

静态槽是一种 ABI 选择，不等同于本次实际错译。但如果同一静态参数存储在前台与 ISR 中重入使用，后者可能覆盖前者的尚未消费参数；即使 ISR 完整保存寄存器也不能保护这类共享内存。

本次没有触发该危险场景，因此不能把长测 PASS 理解为“任意函数可同时从主程序与 ISR 调用”。也没有在本次对所有相关诊断做完整审计，不能笼统宣称任何不安全用法都无诊断。

### 建议与验收

近期建立清晰的 ABI 可重入规则和已知危险调用关系诊断；分析无法覆盖间接调用、跨文件或运行时库时显式说明边界。长期考虑栈传参或函数级可重入方案，涉及 ABI 变化时必须有版本和互操作约束。

验收应覆盖前台/ISR共用helper、低/高ISR共用helper、跨TU多参数、间接调用、隐式libcall。不能仅检查直接调用就宣称整条调用链安全。

## 6. E3：低地址分配受限，错误诊断缺少可操作信息

### 观察

开发中遇到：

```text
cannot allocate .mcs251.dseg
cannot allocate .mcs251.DSEG.7
```

[LinkerCore.cpp](../../../lld/MCS251/LinkerCore.cpp) 的 `layoutData()`（本次核对约1125–1136行）将普通DSEG分配窗口限制在低0x80以内。初期夹具保留范围过大，占用了普通参数槽所需的低地址空间；最终改成三个显式DATA保留区解决。

当前布局为：0030..0064快照/控制，0100..010F错误记录，0580..08FF测试栈与guard，参数槽0065..006F，正常C栈SPX=090F。

### 判断

分配失败不是无缘无故的链接器错误：夹具的初期布局确实与当前分配窗口冲突。问题在于内存模型能力与使用体验，而不是“G12有4K RAM，所以链接器理应把所有direct访问任意放到4K里”。扩大范围必须同时解决寻址语义和ABI兼容，不能简单改上限。

### 建议与验收

错误应包含对象/符号、请求字节数、对齐、可用窗口、已占用区间和冲突来源。若提供更大数据模型，应清楚区分direct、间接访问与栈的放置规则，并校验代码生成匹配。

验收包括无空间、碎片、对齐、固定保留冲突等负向用例；错误信息应足以让用户不阅读链接器实现就能调整布局。

## 7. E4：手写汇编与 ELF 链接路径缺少顺畅衔接

### 观察

本次采用sdas251生成.rel，而C生成ELF。为接入ISR链接流程，[gen-sentinel.py](gen-sentinel.py) 先把哨兵汇编链接成机器码，再用YAML包装为ELF .text，并附ABI note与DATA保留。

该方案刻意要求哨兵内部无外部符号调用和绝对内部跳转，仅用相对分支，避免包装时丢失重定位语义。不是可任意推广的通用汇编对象转换器。

开发中 `.mcs251.CSEG` 等节名被拒绝，随后按链接器规定改用 `.text`；这是夹具的接口使用错误，不单独登记为编译器缺陷。

### 建议与验收

提供明确受支持的汇编→ELF标准路径，支持符号、重定位、ABI信息和调试位置。这个需求不一定只能通过某一种实现满足；本次并未审计所有可能存在的替代工具。

验收至少覆盖跨对象调用、绝对与相对跳转、数据引用、函数大小和ABI不匹配诊断，不只验证无重定位裸代码的包装。

## 8. E5：最终 ELF 与错误信息的可追溯性不足

### 观察

本次对链接后的ELF执行 `llvm-readobj --symbols`，显示空符号列表。输入 `isr.o` 仍有 `_timer0` 符号，最终检查只得结合输入对象和map的节地址定位函数。[check.py](check.py) 保留了这一处理。

分支错误同时仅显示 `<unknown>:0`。两者使“哪段C生成了哪段有问题的机器码”的定位更困难。

### 判断与建议

这是本次构建路径的产物行为，不足以证明所有模式都无法输出调试信息。建议最终ELF默认或可选保留符号，map提供函数级地址、大小，诊断关联具体函数/源码位置，并提供可用于审计的反汇编。

验收应能从最终ELF定位ISR与helper，检查符号值和范围与向量一致；至少在目标地址异常时无需依赖临时对象拼接信息。

## 9. V1：PSW1 差异需独立定位，不能以 PASS 掩盖

### 观察

单次和长测均有：

```text
PSW_RAW=00/00 PSW1_RAW=00/20
FLAGS=NOT_TESTED
```

### 当前结论

差异是实测事实；原因尚未确定。本版故意不把flags纳入PASS，尚未完成对设值、等待、ISR、返回及采样全过程的标志副作用核验。可能涉及夹具、芯片标志语义或恢复路径，当前不能选定其中之一。

### 验证建议

逐条核对等待/采样机器码的标志影响，设置多个合法非零标志组合，建立无扰动的中断前后快照，对照手册及实板。必要时比较无中断基线、手写最小ISR与编译器ISR；对照必须保持待验证之外的条件一致。

验收需要解释00→20，并对所有声称支持的可见标志位给出实板证据；不允许直接屏蔽0x20以制造PASS。

## 10. V2：高寄存器与嵌套等仍有覆盖缺口

- 当前检查R0–R31返回值，但ISR/helper主要使用低寄存器。某个高寄存器未实际被修改时，保存恢复缺陷可能不被检测到。
- 10000次增加了重复执行的可靠性证据，没有自动增加状态组合或抢占窗口覆盖。
- 本版没有两级嵌套，不涉及低→高→低→主的分别恢复。
- 无逐指令抢占窗口，未覆盖序言/尾声执行一半时进入高优先级ISR。
- 没有动态故障注入证明每个检测器都能发现对应错误。

建议通过合法ABI helper和可核实的寄存器压力代码建立主动破坏证据，不能让普通helper违反callee-saved约定后把由此引起的错误归因于ISR编译器。嵌套和标志验证应分开交付，防止多个未知因素叠加。

## 11. 优先级与处置原则

1. **先处理E1：** 归档最小分支越界复现，定位并修复，不长期依赖noinline。
2. **并行澄清E2和V1：** 可重入边界影响应用安全，PSW1差异影响中断正确性结论。
3. **补V2：** 在单层实板通过的基础上增加主动破坏与两级嵌套，而非单纯加大循环次数。
4. **完善E3–E5：** 改善链接诊断、汇编ELF衔接和符号调试能力，降低后续定位成本。

以上是建议排序，不表示这些修复已经实施。本文不修改编译器、固件、冻结manifest或正式board-results验收状态。

## 12. 最终评价

本次应保留的正面结论是：**当前工具链生成的Timer0 ISR、局部数组和跨文件helper，在G12K128特定测试配置下完成了10000轮单层现场恢复检查。**

应保留的限制是：**编译器仍需要用户迁就分支规模、ABI可重入和低地址内存布局；flags、嵌套及完整恢复窗口尚未验证。** 将工程不足、设计限制和待验证项分开记录，比把所有问题统称为“编译器bug”更有助于安排修复和避免误判。
